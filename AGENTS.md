# AGENTS.md — AI Software Factory

Этот файл описывает роли AI-агентов, работающих над проектом, их зоны ответственности и правила взаимодействия. Любой агент (человек или LLM) работает строго в рамках своей роли.

---

## Роли и зоны ответственности

### Product Owner (PO)
**Ответственность:** ценность для пользователя, приоритеты, приёмочные критерии.

- Формулирует задачи в виде GitHub Issues с типом `feature` или `bug`.
- Определяет критерии приёмки (Acceptance Criteria) в теле Issue.
- Единственная роль, переводящая задачу в статус **DONE**.
- Может вернуть задачу на **REWORK** из **QA** или **ACCEPTANCE**.
- Не пишет код и не редактирует конфигурацию деплоя.

### Technical Lead (TL)
**Ответственность:** техническое качество, архитектурная целостность, review PR.

- Проводит Architecture Review и переводит задачу **ANALYSIS → ARCHITECTURE**.
- Единственная роль, дающая **APPROVAL** на начало разработки.
- Проводит Code Review всех PR; без его одобрения PR не мержится.
- Следит за соответствием CLAUDE.md и актуальностью документации.
- Не мержит PR самостоятельно — мержит только через GitHub UI после всех approvals.

### Analyst (AN)
**Ответственность:** декомпозиция требований, детальная постановка задачи.

- Переводит Issue из **NEW → ANALYSIS**, уточняет требования.
- Документирует edge cases, зависимости, ограничения в комментарии к Issue.
- Формирует финальное описание задачи для Architect.
- Не принимает архитектурных решений.

### Architect (AR)
**Ответственность:** проектирование решения, выбор подходов.

- Проектирует решение на этапе **ARCHITECTURE**.
- Описывает архитектурные решения в комментарии к Issue (ADR-lite).
- Определяет файлы, которые будут изменены, и потенциальные риски.
- Не реализует код — передаёт спецификацию Developer.

### Developer (DEV)
**Ответственность:** реализация, юнит-тесты, документация изменений.

- Работает только в своей feature-ветке (формат: `feat/<issue-number>-<slug>`).
- Создаёт PR по шаблону `.github/pull_request_template.md`.
- Не пушит напрямую в `main`.
- Не меняет `fly.toml`, `Dockerfile`, `Procfile` без явного указания TL.
- Не добавляет секреты в код — только через `os.environ.get(...)`.

### QA / Security (QA)
**Ответственность:** качество, безопасность, соответствие критериям приёмки.

- Запускает тесты (`python test_smoke.py`) и проверяет CI.
- Проверяет отсутствие секретов (Gitleaks, `test_no_hardcoded_secrets`).
- Переводит задачу **DEVELOPMENT → QA → ACCEPTANCE** или возвращает на **REWORK**.
- Оставляет замечания в PR Review с конкретными строками кода.

## Workflow статусов

```
NEW → ANALYSIS → ARCHITECTURE → APPROVAL → READY → DEVELOPMENT → QA → ACCEPTANCE → DONE
                                                                  ↓
                                                               REWORK → DEVELOPMENT
```

| Статус       | Метка Issue       | Кто переводит | Условие перехода                                   |
|--------------|-------------------|---------------|--------------------------------------------------|
| NEW          | `status: new`     | PO/любой      | Issue создан                                      |
| ANALYSIS     | `status: analysis`| AN            | PO подтвердил приоритет                           |
| ARCHITECTURE | `status: arch`    | AR            | AN завершил декомпозицию                          |
| APPROVAL     | `status: approval`| TL            | AR описал архитектуру, TL одобрил подход          |
| READY        | `status: ready`   | TL            | APPROVAL получен, DEV назначен                    |
| DEVELOPMENT  | `status: dev`     | DEV           | DEV открыл PR, привязал к Issue                   |
| QA           | `status: qa`      | QA            | PR создан, CI зелёный                             |
| ACCEPTANCE   | `status: acceptance`| PO          | QA без замечаний, все чеклисты PR выполнены       |
| DONE         | `status: done`    | PO            | PO принял результат, PR смержен                   |
| REWORK       | `status: rework`  | QA или PO     | Замечания в PR Review; возврат → DEVELOPMENT      |

---

## Правила взаимодействия

1. **Один агент — одна роль.** Не совмещать DEV и QA для одной задачи.
2. **Коммуникация через GitHub.** Все решения и замечания — в комментариях Issue или PR Review, не в чате.
3. **Не мержить без полного чеклиста.** Все пункты PR-шаблона должны быть отмечены.
4. **Секреты только в переменных окружения.** Нарушение блокирует PR.
5. **Ветки от main.** Каждая задача — своя ветка, PR в main.
6. **Не менять бизнес-логику в инфра-задачах.** Инфраструктурные PR не трогают `main.py`, `mymeet_sync.py`, `db.py`, `auth.py`, `gtasks.py`.
7. **REWORK не сбрасывает прогресс.** DEV фиксирует правки в том же PR (новые коммиты, не force-push без согласования TL).

## Матрица полномочий (RACI)

| Действие                     | PO  | TL  | AN  | AR  | DEV | QA  |
|------------------------------|-----|-----|-----|-----|-----|-----|
| Создать Issue                | A/R | I   | R   | I   | I   | I   |
| Уточнить требования          | C   | C   | A/R | I   | I   | I   |
| Описать архитектуру          | I   | C   | C   | A/R | I   | I   |
| Дать APPROVAL                | I   | A/R | I   | C   | I   | I   |
| Написать код / тесты         | I   | C   | I   | C   | A/R | I   |
| Провести Code Review         | I   | A/R | I   | C   | I   | C   |
| Провести QA / Security check | I   | C   | I   | I   | I   | A/R |
| Принять задачу (DONE)        | A/R | C   | I   | I   | I   | C   |
| Смержить PR                  | I   | A/R | I   | I   | I   | I   |

> **A** = Accountable (отвечает), **R** = Responsible (выполняет), **C** = Consulted, **I** = Informed
