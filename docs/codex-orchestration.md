# Оркестрация проекта в Codex

Открой доверенный checkout проекта в Codex CLI командой `codex` или начни новый сеанс Codex в корне репозитория. Передай одну задачу целиком: «Выполни `$zinochka-task`. Цель … Критерии приёмки … Ссылка на issue …». В интерактивном интерфейсе навык можно выбрать через `/skills`. Если клиент его не обнаружил, попроси оркестратора прочитать этот файл и `AGENTS.md` и использовать нативных субагентов по опубликованным профилям. Если клиент не подхватил профили проекта, передай текст конкретного TOML в отдельный нативный поток и зафиксируй отличия выданных инструментов. Независимые проверки и разрешения обязательны в обоих режимах.

## Передача работы

Политика уровней, выпуска и отката находится в [AGENTS.md](../AGENTS.md). Профили в `.codex/agents/` задают задачи и формат результата, а навык в `.agents/skills/` задаёт порядок передачи. Codex вызывает нативных субагентов от имени основного сеанса. Глубина вложенности ограничена одним уровнем; оркестратор контролирует владение файлами и завершение агентов. Единственный писатель участка — Developer или назначенный оркестратор. Для независимого QA передай оригинальные критерии, зафиксированное состояние исходников, base SHA и способ получить diff; после исправлений передай новую ревизию для повторной проверки. Security проверяет тот же снимок. DevOps проверяет инфраструктурные изменения и сверяет удалённые jobs после push. Выпуском управляет только основной сеанс.

Профили сокращают набор инструментов через `features`; Architect получает файлы и необходимые сведения от оркестратора. Песочница и правила подтверждений наследуются от основной сессии. Роли с shell используют перечисленные в профиле границы по инструкции. Для технически принудительного чтения используй изолированную read-only среду или передай агенту подготовленный diff и результаты безопасных команд без доступа к исходному checkout. Используй существующие GitHub-права оркестратора для ветки и PR, доступ Fly для наблюдения только при наличии ранее разрешённого режима чтения. [Схема профилей Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agent-file-schema)

## Проверки и выпуск

- Локально запусти `make test` с фиктивными переменными в очищенном окружении и `python3 ci/check_docker_packaging.py`. При доступном Docker запусти `bash ci/docker_import_smoke.sh`. Команда запуска бота для такой проверки не нужна.
- Для CI сопоставь `gh pr view <PR> --json headRefOid,baseRefName,statusCheckRollup` и `gh pr checks <PR>` с проверенным SHA. Сохрани ссылки на Smoke tests, Docker packaging, Gitleaks и остальные обязательные проверки GitHub. При отказе инструмента или недоступности GitHub используй доступный штатный канал чтения, зафиксируй оставшиеся пробелы и сохрани gate закрытым.
- Для уровня 2 передай независимому аудитору ChatGPT PR, точный head SHA, отчёты QA/Security, CI и непроверенные сценарии. До разрешений из AGENTS.md оставь PR открытым. Утверждение относится только к проверенной ревизии. Для разрешённого merge через CLI передай `--match-head-commit <проверенный-SHA>`. Запрещены обход защиты ветки и отложенный auto-merge.
- После разрешённого merge наблюдай за текущим production workflow по merge SHA. Артефакт `deploy-monitor-report` и job summary дают результат проверки. Merge в main запускает deploy даже для изменений одной документации.

## Аудит перехода

Ранее `/task` связывал Architect, Developer, QA, DevOps и Deploy Monitor. Developer публиковал PR, QA проверял diff и возвращал дефекты на исправление, DevOps проверял инфраструктуру, Deploy Monitor сверял выпуск. GitHub подтверждает практику архитектурной проработки и QA, а также реальные инциденты мониторинга. Факт запуска конкретной slash-команды по этой истории установить нельзя. [Задача №14](https://github.com/AnatoliyZakharov/ZinaidaSergeevnaBot/issues/14), [результат QA №38](https://github.com/AnatoliyZakharov/ZinaidaSergeevnaBot/issues/38), [инцидент №45](https://github.com/AnatoliyZakharov/ZinaidaSergeevnaBot/issues/45)

Перенесены раздельные роли, цикл исправлений QA и проверка выпуска по артефакту. Публикация PR перешла к оркестратору. Security Reviewer выделен в самостоятельную роль. Дублировавшиеся условия выпуска в CLAUDE.md, /task и PR-шаблоне заменены ссылками на AGENTS.md. В архиве остаются историческая запись проверки восстановления, старое значение AUTO_RELEASE_READY и прежние инструкции. Старые комментарии Validate docs о будущем включении CI уже не отражают состояние проекта. Корневой CLAUDE.md сохранён для существующей проверки наличия файла. Workflows, Dockerfile, Fly и код бота сохранены.

## Приёмочная репетиция

Выполняй репетицию в отдельной рабочей копии или на временных фикстурах. Если нужен тест сетевой публикации, используй отдельную рабочую ветку и draft PR. Для каждого сценария запиши вход, проверенный SHA или фикстуру, выполненные команды, наблюдаемый результат и пробелы.

| Сценарий | Наблюдаемый критерий |
| --- | --- |
| Правка документации | Architect формулирует критерий, Developer вносит правку, QA и Security выдают заключения на одном снимке, оркестратор готовит PR. Репетиция завершается до merge. |
| Дефект QA | Независимый QA возвращает FAIL на намеренно неверном тексте. Developer исправляет; QA проверяет тот же критерий и выдаёт PASS на новой версии. |
| Уровень 2 | PR остаётся открытым на проверенном SHA. Запуск deploy и merge отсутствует. |
| Уровень 3 | Для сценария без разрешения PO фиксируется блокировка до правок, PR и любых внешних мутаций. |
| Ошибка CI или GitHub | Неуспешная или недоступная проверка блокирует выпуск; отчёт сохраняет причину и фактический статус. |
| Секреты и production | Проверяй изменения без вывода совпадений. Gitleaks и результат независимого Security укажи отдельно. История действий репетиции не должна содержать merge, dispatch, Fly-мутаций или старта бота. |
