# /task — Выполнение задачи

Запускает полный цикл разработки по задаче из GitHub Issues.

**Использование:** `/task <issue-number>`

---

## Флаг готовности автономных релизов

**AUTO_RELEASE_READY = false**

Пока этот флаг `false`, НЕ выполняй автоматический merge и deploy даже для Уровня 1. Вместо этого: выполни все шаги до merge, сообщи Product Owner о готовности, дождись явного разрешения.

Флаг становится `true` только после того, как Product Owner явно сообщает: «AUTO_RELEASE_READY = true» — подтвердив, что снапшоты volume `bot_data` проверены и восстановление из них работает.

---

## Уровни автономности

Определи уровень **до начала работы**:

- **Уровень 1** — обычные изменения кода, тесты, документация, рефакторинг
- **Уровень 2** — auth/OAuth, права доступа Google, изменения хранения данных в БД, CI/CD пайплайн, `crypto.py`, логика clear/overwrite в `mymeet_sync.py`
- **Уровень 3** — удаление/необратимые преобразования данных, миграции с риском потери данных, ротация `ENCRYPTION_KEY`, удаление volumes Fly.io, новые расходы

**При неопределённости — применяй более строгий уровень.**

Запости план в issue, подставив реальный результат архитектора:

Если архитектор вернул `NEEDS CLARIFICATION` — остановись и сообщи Product Owner. Не начинай разработку.

---

## Шаг 2 — Разработка

Запусти агента `developer`. Передай ему:
- Текст задачи и критерии приёмки
- Архитектурный анализ из Шага 1

Разработчик создаст ветку, реализует изменения и создаст PR. Получи от разработчика номер созданного PR — используй его во всех последующих шагах.

---

## Шаг 3 — QA

Запусти агента `qa-engineer`. Передай ему:
- Номер PR (реальный номер из Шага 2)
- Текст задачи и критерии приёмки
- Архитектурный анализ

QA читает реальный diff (`git diff main...HEAD`), запускает `python test_smoke.py`, проверяет каждый критерий приёмки.

При FAIL:

---

## Шаг 4 — Цикл исправлений (только при FAIL)

Если QA вернул FAIL — запусти разработчика на устранение конкретных блокеров из заключения QA. Максимум 2 цикла исправлений.

После каждого исправления повторяй Шаг 3 заново.

Если после второго цикла QA всё ещё FAIL:

Остановись полностью. Не продолжай без участия Product Owner.

---

## Шаг 5 — DevOps-проверка (только если изменена инфраструктура)

Выполняй **только** если изменены: `fly.toml`, `Dockerfile`, `Procfile`, `.github/workflows/`, `requirements.txt`.

Запусти агента `devops`. Передай ему номер PR и список изменённых файлов инфраструктуры.

---

## Шаг 6 — Финальное действие

### При Уровне 1 И AUTO_RELEASE_READY = true

Убедись, что выполнены все условия одновременно:

- [ ] CI зелёный — проверь реальный статус: `gh run list --workflow=smoke-tests.yml --limit 3`
- [ ] QA вернул PASS
- [ ] Нет известных BLOCKER
- [ ] Секреты в коде не обнаружены

Если все выполнены — выполни merge (подставь реальный номер PR):

Проверь фактический статус деплоя — не HTTP-ответ, а GitHub Actions:

Запости итог в issue с реальными данными:

### При Уровне 1 И AUTO_RELEASE_READY = false

Выполни все шаги до Шага 5 включительно. Затем:

Остановись. Жди подтверждения.

### При Уровне 2

Выполни все шаги до Шага 5. Затем:

Остановись. Жди подтверждения Product Owner.

### При Уровне 3

Остановись немедленно после Шага 1, не начиная разработку:

Остановись. Не выполняй операцию.

---

## Правила для всех шагов

- Никогда не удалять `/data/bot.db` и volumes Fly.io
- Никогда не запускать второй экземпляр бота
- Никогда не выводить значения секретов в комментарии или логи
- Не расширять scope задачи — фиксируй дополнительные проблемы отдельными issues
- Успешный HTTP-ответ `/health` не является доказательством успешного деплоя — используй `gh run list`
