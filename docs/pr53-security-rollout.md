# Подготовка перехода безопасности PR №53

Этот план применяется только после независимого аудита точного SHA, зелёного CI и отдельного разрешения владельца на выпуск. Разработка и проверки выполняются на синтетических данных. GitHub Rulesets и production не участвуют в репетиции.

## Совместимость перед переключением

| Сценарий | Ожидаемый результат | Проверяемое доказательство |
| --- | --- | --- |
| Прежние Google Calendar и Tasks | Старый грант читается. Незавершённое подключение, отказ callback и неверное подтверждение не заменяют токены. | Моки Google и Telegram, проверка старого снимка SQLite после каждого отказа. |
| Ранее настроенная таблица | ID, токен MYmeet и настройки остаются в БД. Запись запрещена до подтверждения этой таблицы действующим пользовательским грантом. | Нулевая запись на старом гранте, сохранение строк конфигурации. Проверить ручной, полный, плановый импорт и личный лист. |
| Подтверждённая таблица | Проверены доступ приложения к файлу и возможность редактирования у пользователя. Пишет делегированный аккаунт. | Моки Drive и Sheets с разрешением и отказами. Сверка адресата и неизменности соседних листов при повторах и сбоях. |
| Старые и новые токены SQLite | Совместимое чтение, повторный запуск преобразования и отказ с сохранением записей при неверном ключе. | Изолированная копия SQLite, отдельный тестовый ключ, сравнение снимков и восстановление резервной копии. |

`drive.file` ограничивает доступ файлами, явно разрешёнными приложению. Ввод ID или ссылки выбирает уже разрешённый файл. Сам по себе ID доступа не выдаёт. До выпуска необходимо подтвердить штатный механизм открытия существующих таблиц в OAuth-приложении, например Google Picker или Open With, на отдельных тестовых аккаунтах. Реальный доступ, включение API и настройки Google-проекта в этой разработке не проверяются. Защита отдельных диапазонов действует и при успешной проверке файла.

Перед выпуском потребуется согласовать окно подтверждения существующих таблиц и порядок связи с пользователями. Записи с неподтверждённым назначением сохраняются и остаются недоступными для записи. Потеря доступа на запись таким пользователям считается блокером общего переключения, пока переход не отрепетирован.

## Резервная копия и восстановление

1. Перед разрешённым выпуском подтвердить свежий снимок `bot_data` и доступность исходного ключа по действующему процессу хранения секретов. Не выводить ключи, токены, персональные данные или строки таблиц в CI и отчёты.
2. Восстановить снимок в отдельную изолированную среду без Telegram polling и доступа к реальным Google/MYmeet. Для SQLite с WAL использовать согласованный snapshot или SQLite Backup API. Копирование только открытого файла БД может пропустить изменения из WAL.
3. Сверить `PRAGMA integrity_check`, версию схемы и обезличенные инварианты настроек. На синтетической копии проверить повтор преобразования, неверный ключ, сбой записи и восстановление. Отсутствие ключа и повреждённый шифротекст не исправляются записью нового значения поверх старого.
4. Проверить читаемость новой БД выбранной версией восстановления. Когда в копии нет ни одного проверяемого зашифрованного свидетеля, преобразование требует подтверждённого отпечатка ключа из доверенного источника. При отсутствии доказательства старые токены читаются, а их перезапись блокируется; это может отложить обновление истёкшего access token. Старая версия до поддержки конверта токена не сможет прочитать новый формат. До переключения сохранить обратимо совместимую копию и согласовать стратегию для записей, появившихся после снимка.

## Выпуск и откат

- До merge зафиксировать аудит проверенного head, зелёный CI, решение владельца по переходу и доступный путь восстановления. Merge в main запускает production workflow.
- После отдельно разрешённого выпуска сверить merge SHA, CI preflight и отчёт Deploy Monitor. На согласованных тестовых аккаунтах проверить старые Calendar/Tasks, привязку Google в личном чате, разрешённый тестовый файл и отказ без записи.
- Изменение `db.py` исключает штатный автоматический откат по текущей политике. При отказе остановить дальнейшее развёртывание, сохранить текущее состояние и передать решение PO. Не запускать старый образ поверх БД с новыми конвертами без подтверждённой совместимости. Восстановление копии и повторный выпуск требуют отдельного решения.
- По предварительной проверке GitHub ветка main оставалась без активной защиты. Включение правил GitHub находится за пределами разработки. До выпуска требуется перепроверить защиту и используемый процесс независимого ревью.
