# /task — Выполнение задачи

Запускает полный цикл разработки по задаче из GitHub Issues.

**Использование:** `/task <issue-number>`

---

## Флаг готовности автономных релизов

**AUTO_RELEASE_READY = true**

Пока этот флаг `false`, НЕ выполняй автоматический merge и deploy даже для Уровня 1. Вместо этого: выполни все шаги до merge, сообщи Product Owner о готовности, дождись явного разрешения.

Флаг становится `true` только после того, как Product Owner явно сообщает: «AUTO_RELEASE_READY = true» — подтвердив, что снапшоты volume `bot_data` проверены и восстановление из них работает.

---

## Уровни автономности

Определи уровень **до начала работы**:

- **Уровень 1** — обычные изменения кода, тесты, документация, рефакторинг
- **Уровень 2** — auth/OAuth, права доступа Google, изменения хранения данных в БД, CI/CD пайплайн, `crypto.py`, логика clear/overwrite в `mymeet_sync.py`
- **Уровень 3** — удаление/необратимые преобразования данных, миграции с риском потери данных, ротация `ENCRYPTION_KEY`, удаление volumes Fly.io, новые расходы

**При неопределённости — применяй более строгий уровень.**

## Шаг 5 — DevOps-проверка (только если изменена инфраструктура)

Выполняй **только** если изменены: `fly.toml`, `Dockerfile`, `Procfile`, `.github/workflows/`, `requirements.txt`.

Запусти агента `devops`. Передай ему номер PR и список изменённых файлов инфраструктуры.

Независимо от того, вызывался ли DevOps, CI job **«Docker packaging»** (`smoke-tests.yml`) обязан быть зелёным: он проверяет, что все локальные модули, нужные entrypoint, копируются в образ, собирает образ и импортирует модули внутри него. Тот же контроль повторяется в preflight `deploy.yml` и блокирует деплой.

## Шаг 7 — Deploy Monitor (после каждого merge в main)

Порядок релиза: QA → Security → DevOps → решение Product Owner (по правилам уровня) → merge → deploy → **Deploy Monitor** → итоговый отчёт. После merge ответственность оркестратора не заканчивается. Правила разрешения merge и deploy этим шагом не меняются.

1. Получи merge-SHA: `gh pr view <PR> --json mergeCommit --jq .mergeCommit.oid`.
2. Запусти агента `deploy-monitor`, передай ему merge-SHA и номер PR. Агент находит run `deploy.yml` по SHA, ждёт job «Deploy Monitor» (10 минут наблюдения от старта новой версии, автооткат при FAILED по утверждённым условиям), скачивает артефакт `deploy-monitor-report`, перепроверяет Fly.io только чтением и возвращает статус `HEALTHY` / `DEGRADED` / `FAILED` / `ROLLED_BACK` / `UNKNOWN`.
3. Жди результата агента. Промежуточных подтверждений у Product Owner не запрашивай.
4. Если дождаться невозможно (сессия завершается) — зафиксируй в issue строку «контролируемое ожидание: run <url>» и сверь результат в начале следующей сессии.
5. Итоговый отчёт дополни строкой: **Deploy Monitor:** `<статус>` (ссылка на run и incident issue, если есть).
6. `FAILED` / `UNKNOWN` — срочно сообщи Product Owner с отчётом агента; `ROLLED_BACK` — релиз не выпущен, заведи fix-задачу; `DEGRADED` — сообщи PO и заведи issue. Повторный деплой и ручной откат — только по решению Product Owner.

Агент и оркестратор не выполняют `flyctl deploy`/rollback вручную: откат делает только workflow. Аварийное отключение автооткатов — repository variable `AUTO_ROLLBACK_DISABLED=true`.

---

## Правила для всех шагов

- Никогда не удалять `/data/bot.db` и volumes Fly.io
- Никогда не запускать второй экземпляр бота
- Никогда не выводить значения секретов в комментарии или логи
- Не расширять scope задачи — фиксируй дополнительные проблемы отдельными issues
- Успешный HTTP-ответ `/health` и зелёный шаг deploy не являются доказательством успешного релиза — используй статус Deploy Monitor (Шаг 7)
